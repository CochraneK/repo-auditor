# P0 · 阻断项

## 1. “原题 / baseline”目前并不是真正的标准 baseline

### 证据

`app.js` 中：

- PCL-5 中文文本明确是原型转述；
- Current CAPE-P15 中文同样不是验证中文版；
- CAPE-P15 当前只实现频率层，没有实现 associated distress。

`README.md` 自己也明确承认这些限制。

### 问题

如果 baseline 本身已经发生了语言改写或结构删减，那么后续：

- 原题 vs 情景版；
- 原题 vs SJT；
- 原题 vs PsychoGAT；

就不能严格解释为“标准量表 vs 改编版”。

### 建议

在拿到合规、验证过的目标语言版本之前：

- 把 UI 中的 **“原题”** 改成更准确的名字，例如：
  - `minimal-presentation condition`
  - `direct-question condition`
  - `plain questionnaire condition`
- 不要把它称为 psychometric gold-standard baseline。
- 正式研究时再单独建立 `validated-baseline`。

---

## 2. 研究问题过多，8 种模式不能一次同时回答

当前 8 种模式实际上改变了不同层级：

| 层级 | 模式 |
|---|---|
| 只改体验外壳 | VASSIP、Emoji |
| 改 item 呈现 | item-level scenario |
| 改构念测量形式 | construct SJT |
| 改题目生成过程 | AI-SJT |
| 改连续任务结构 | PsychoGAT-lite、RUSH |

这些不是一条单一的“游戏化程度”连续轴。

### 风险

如果把它们放进同一个实验比较，会同时混入：

- 题目措辞变化；
- item 数量变化；
- response format 变化；
- 记忆/上下文效应；
- 叙事连续性；
- 反应选项数量变化；
- 评分权重变化；
- 任务长度变化。

最后即使发现“某模式更好玩 / 分数更低 / 完成率更高”，也很难知道原因是什么。

### 建议

第一阶段只保留 **最多 3 个条件**：

1. direct-question / baseline-like condition
2. VASSIP 或 Emoji（二选一，代表低改编）
3. item-level scenario（代表中改编）

其余：

- construct SJT
- AI-SJT
- PsychoGAT-lite
- RUSH

移入 **Advanced experiments / Phase 2**。

---

## 3. 目前是 Demo，不是研究运行器

当前仓库没有看到研究收数所需的关键基础设施：

- participant/session ID；
- 条件随机分配；
- 顺序平衡 / counterbalancing；
- task version；
- item-bank version；
- 开始/结束时间；
- item response latency；
- 中途退出记录；
- 数据导出 schema；
- consent / withdrawal 记录；
- 研究版本冻结；
- protocol version。

### 风险

即使 UI 能完成测评，也很难得到可复现、可审计的数据。

### 建议

在正式研究前新增明确的：

`study-manifest.json`

至少记录：

```text
study_version
scale_version
language_version
mode_version
item_bank_version
condition
condition_order
participant_id
session_id
started_at
completed_at
```

---

## 4. Future Me 应从核心测评比较中拆出

`future-me/` 的目标是：

- 人生故事访谈；
- synthetic memory；
- future-self chat；
- reflection / action。

它和“心理测评交互形式比较”不是同一个研究问题。

### 建议

优先级从高到低：

1. 最好拆成独立 repository；
2. 或保留同仓，但成为完全独立的 `labs/future-me/`；
3. 首页不要把它与量表模式放在同一实验选择层。

当前它更像**反思干预 / generative experience**，不是 assessment mode。

---

## 5. Future Me 存在 DOM 渲染安全问题

### 证据

`future-me/app.js`：

- 表单自由文本写入 `state.profile`；
- `buildMemory()` 将这些文本拼进 `state.memory`；
- `renderReady()` 使用 `memorySummary.innerHTML = ...`；
- 该路径没有像聊天消息那样统一走 `escapeHtml()`。

聊天消息本身做了转义，这是好的；但 memory summary / timeline 路径没有保持同一规则。

### 风险

输入 HTML 字符串可能进入 DOM。

当前主要是本机自输入场景，所以外部攻击面有限，但**公开 Demo / 未来接后端前必须修**。

### 建议

统一原则：

> 任何用户输入或模型输出默认使用 `textContent`，只有固定模板本身使用 HTML。

如果必须拼 HTML，则所有动态字段都先 `escapeHtml()`。

# P1 · 高优先问题

## 6. Future Me 的“本地保存”说明还不够

当前已经写了：

- 不是预测；
- 不是治疗；
- 本地优先；
- 默认不上传模型。

这是好的。

但 `localStorage` 会持久保存：

- profile；
- life story；
- synthetic memory；
- messages。

### 需要补充

开始前明确说明：

> 内容会保存在当前浏览器，关闭页面后仍可能存在。共用设备请完成后清空。

并提供：

- visible “清除本地数据”；
- 可选“不保存本地”模式；
- 最好增加存储期限或 session-only 模式。

---

## 7. SJT / PsychoGAT 的答案梯度过于明显

不少场景选项呈现为：

> 明显适应性解释 → 不确定 → 明显症状化解释

例如：

- “算法巧合”
- “怀疑设备与想法有关”
- “很确定设备能读取思维”

这会导致明显的：

- demand characteristics；
- social desirability；
- construct transparency。

参与者很容易猜到“哪一个答案意味着症状更高”。

### 建议

- 增加 distractor dimensions；
- 不要每题都严格从“健康 → 症状”单向排列；
- 平衡 keying；
- 对选项自然度做专家评分；
- 随机化选项顺序时谨慎处理 ordinal meaning；
- 先做认知访谈，而不是直接大样本。

---

## 8. 当前自定义权重没有心理测量依据

代码里可见：

- construct mode 常用 `0 / 2 / 4`；
- AI-SJT 使用 `[0,1,2,4]`；
- PsychoGAT-lite 主要是 `0 / 1`；
- RUSH 也使用自定义信号权重。

这些可以作为游戏内部 signal，但不能当作量表分值。

当前文案多数已经做了免责声明，这是优点。

### 建议

代码层把变量名从：

`score`

尽量改成：

`signal` / `choice_key` / `prototype_weight`

防止未来误用。

---

## 9. experiments.js 的扩展方式过于脆弱

### 当前结构

`experiments.js`：

1. 保存 `LEGACY_MODES = {...MODES}`；
2. 删除原 `MODES`；
3. 重新 `Object.assign`；
4. 保存旧 `resetRun`；
5. 覆写 `resetRun`；
6. 保存旧 `renderStep`；
7. 再覆写 `renderStep`。

### 风险

- script 顺序一变就容易坏；
- app.js 改函数名就容易坏；
- 模式之间依赖隐藏；
- 很难单测；
- 很难知道最终 runtime 到底有哪些 mode。

### 建议

重构为显式模式注册表：

```js
const modes = {
  original: {...},
  vassip: {...},
  itemscene: {...}
}
```

每个 mode 实现统一接口，例如：

```text
start()
renderStep()
handleAnswer()
finish()
```

## 10. 没有测试，CI 只有部署

当前 `.github/workflows/pages.yml` 只做：

- checkout；
- upload Pages artifact；
- deploy。

没有：

- JS syntax check；
- smoke test；
- mode registry check；
- item count check；
- score range check；
- link check。

### 建议最低限度加入

- 每个量表 item count；
- 每个情景版 item count；
- 所有 mode 可初始化；
- 所有 mode 可完成；
- PCL-5 range 0–80；
- CAPE 当前实现 range 15–60；
- 没有 undefined scene；
- README 宣称的 mode 数 == runtime mode 数。

# 已经做得好的地方

这次审计不是“全部推倒”。

项目里已经有几个非常重要的正确方向：

- 多处明确写 **“不是诊断”**；
- 明确区分正式量表分数与 experimental signal；
- AI-SJT 当前使用冻结题库，而不是每次在线随机生成，利于复现；
- Future Me 明确写“不是预测”“不是治疗”；
- Public Demo 默认不直接调用在线 LLM；
- Future Me 聊天消息已经使用 `escapeHtml()`；
- README 已经记录主要研究来源；
- PCL-5 / CAPE 的限制没有被隐藏；
- Pages 部署简单，原型迭代成本低。

所以方向不是“删除重来”，而是：

> **减少范围，建立边界，把已经有的好原型变成可以验证的研究工具。**
